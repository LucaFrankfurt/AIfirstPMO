# Modules

[`architecture.md`](architecture.md) says how Kolibri is built: four packages, one registry, one
write path, no runtime dependencies on the server. That is the *horizontal* story — the layers, and
what each of them is allowed to know.

This file is the *vertical* one. It asks a different question of the same code: **where does one
capability live, and what would it cost to add another one, switch one off, or take one out?** The
answer today is "in ten files, three of which are the largest in the repository", and the rest of
this document is about which ten, why it happened, and what shape fixes it.

It is written to be re-runnable rather than believed. The inventory in the next section is
*generated* by `scripts/modules.mjs` and checked by it in CI, so it cannot quietly stop being true;
the same script enforces the four rules at the end.

```bash
npm run check:modules      # the rules, and whether the tables below still match
npm run modules            # the inventory on the terminal
npm run modules -- --fix   # rewrite the tables below
```

Two numbers in those tables are the whole diagnosis. `notifications` is **58 lines** — writing a
notification is one small function, because everything it *means* got distributed into `repo.ts` and
everything it *does* got distributed into five adapters. And `adapter/mcp` is **5 667** — the
assistant's view of the product is a third larger than the product's own largest capability,
because every tool re-derives from SQL what a screen already knows.

## What already works

Four seams in this codebase are load-bearing and should be extended rather than replaced. A
reorganisation that breaks any of them is a worse architecture with a tidier directory listing.

**The entity registry.** `shared/src/entities.ts` — 42 entities, six flags, one line per field —
generates the server's write path, the REST routes, the sync queries, the client's IndexedDB stores
and the merge rules. Adding a field is one line plus a column. This is the single best thing in the
repository and every proposal below is a way of making *more* of the system derive from it, not less.

**Pure domain logic in `shared`.** `budget.ts`, `kpi.ts`, `rates.ts`, `landscape.ts`,
`schedule.ts` — 2 293 lines of arithmetic and rules with no I/O, imported by the server, the web app
and the MCP tools alike. Money is rounded the same way in a screen, in a report and in an export
because there is one function. `shared` imports nothing from `server` or `web`, and the check
enforces it.

**Two real provider interfaces.** `lib/ai.ts` has three model providers behind one `Reviewer` type;
`lib/storage.ts` has disk and S3 behind one interface with the same content-addressed key. Both are
small, both are honest about what varies (`ai.ts`: "the URL, the header the key goes in, where the
prompt sits, where the answer sits"), and both are the template for the adapter ring.

**One write path.** Every mutation — REST, sync push, MCP tool, seed script, automation rule — goes
through `writeEntity`. That is why merge semantics, the activity trail, notifications and the search
index cannot drift apart between entry points. The problem below is not that this exists; it is that
`writeEntity` was made to *contain* what it should *dispatch to*.

## Where it breaks down

### One capability, traced

Budgets is the newest optional feature and the cleanest specimen: it is switched off by default, it
has its own tables, and nothing else in the product needs it. Here is everywhere the word appears
outside its own three files.

| `server/lib/mcp.ts` | 134 | Seven tools, 461 lines |
| `server/lib/repo.ts` | 73 | Invariants, cascades, `canSeeBudget` |

### The findings

Seven of them, each with the evidence and each with a fix, ordered by what they cost.

### 1. `lib/mcp.ts` is a second application

5 464 lines, five exports, 72 tools and 5 prompts in one `TOOLS` array, with **126 raw SQL
statements** inline. By tool group:

| Group | Tools | Lines |
|---|---:|---:|
| Reports | 8 | 729 |
| Planning | 12 | 592 |
| Tasks | 9 | 539 |
| Budgets | 7 | 461 |
| Configuration | 6 | 366 |
| KPIs | 5 | 361 |
| Infrastructure | 6 | 340 |
| Rates | 4 | 229 |
| Pages | 6 | 197 |
| Workspace | 6 | 185 |
| Attachments | 3 | 184 |

Adding a capability means editing this file. Removing one means editing this file. A workspace with
budgets switched off still ships and loads all 461 lines of budget tools, and the switch is checked
per call inside them. The eleven groups map one-to-one onto capability modules that already exist —
this file is a directory listing that was written as an array.

It was also where both of the repository's layering violations lived: `lib/mcp.ts` imported
`storeFile` from `routes/files.ts` and `searchWorkspace` from `routes/search.ts`. **Fixed** — both
moved down into `lib/uploads.ts` and `lib/search.ts`, where the route and the MCP tool are equal
callers of one implementation rather than one of them reaching up into the other. There are now no
layering exceptions at all, which is worth more than two: nothing is left to cite as precedent.

> **Fix.** Each capability owns a `tools.ts` exporting its `ToolDef[]`. `lib/mcp.ts` keeps the
> JSON-RPC envelope, the scope check, the error mapping and the prompts — roughly 400 lines — and
> assembles the tool list from whatever modules are enabled. `check:figures` already counts the
> tools, so the README cannot drift while this happens.

### 2. `lib/repo.ts` contains the rules it should dispatch to

2 370 lines. The generic part — merge, tombstones, references, the transaction — is about 400 of
them. The other 1 900 are domain-specific and belong to capabilities that already exist elsewhere:

| In `repo.ts` | Belongs to |
|---|---|
| `applyBudgetInvariants`, `tombstoneBudgetChildren`, `detachActualsOf`, `canSeeBudget` | `budgets` |
| `applyKpiInvariants`, `tombstoneKpiChildren`, `detachTargetsOf`, `canSeeKpi` | `kpis` |
| `applyLandscapeInvariants`, `detachFromVendor`, `detachComponent` | `infrastructure` |
| `applyRateInvariants` | `time` |
| `applyChannelInvariants`, `applyMessageInvariants`, `guardChannelWrite`, `guardMessageWrite`, `guardReadStateWrite`, `reconcileReactions`, `canSeeChannel`, `notifyLevel` | `chat` |
| `applyPageInvariants`, `snapshotPage`, `mergeCrdt` | `pages` |
| `applyTaskInvariants`, `guardTransition`, `cascadeSchedule` | `work`, `planning` |
| `notify` (172 lines), `fireWebhooks` (172), `taskPayload`, `recordActivity` | `notifications`, `adapter/webhooks` |

`applyInvariants` alone is a 194-line switch over entity names. Every new capability makes it longer,
and every capability that could be removed cannot be, because its rules are interleaved with
everyone else's inside one function.

> **Fix.** `writeEntity` gains four hook points — `defaults`, `invariants`, `guards`, `effects` —
> and a module registers for the entities it owns. The dispatcher stays in the kernel; the rules move
> to the capability that owns them, next to the pure logic in `shared` they already call.

### 3. The write path and the rules engine hold each other up

`repo.ts` → `automation.ts` → `repo.ts`, and `repo.ts` → `automation.ts` → `bootstrap.ts` →
`repo.ts`. Three files that can all reach each other, so none of them can be understood, tested or
replaced alone.

The relationship is real — the write path calls the rules engine and the rules engine writes rows.
What is accidental is only the *import*, and it is worth being precise about which part, because the
obvious fix is wrong.

`afterWrite` says so itself: *"`runAutomations` stays inline on purpose: what it writes must land
inside the transaction, and what those writes notify comes back through here and queues itself."*
Publishing on `lib/bus.ts` and having `automation` subscribe would make that call asynchronous, which
moves a rule's writes outside the transaction and breaks `create_tasks_batch`'s "every task or none"
for exactly the rows a rule generated — the failure `withEffectsHeld` was written to prevent, let
back in through the other door.

> **Fix.** Dependency inversion, not asynchrony. `repo` exposes `onWrite(handler)`; `automation`
> registers itself from the composition point at startup. The call stays synchronous and stays
> inside the transaction, so nothing about the semantics moves — only the import direction. That is
> also the general case of the `effects` hook in the module contract below, so this is not a special
> arrangement for one module: it is the first user of the one every module gets. `withEffectsHeld`
> is untouched, and so is the external-effects queue.

### 4. Three capabilities on the client hold each other up

`budget.tsx` → `insights.tsx` → `rates.tsx` → `budget.tsx`. Budgets borrowed a table from planning,
planning borrowed "may this person see money" from time, and time borrowed a money input back from
budgets. A second knot, `views.tsx` ↔ `saved-views.tsx`, was a view's *shape* living in the screen
that renders it. Underneath both, `components/` holds 53 files from every capability side by side,
so which screen a component belongs to is a guess from its name.

Both knots are **fixed**, and none of it needed the callers rearranged — only the shared thing moved
down to where all of them could reach it: `asMoney` and `MoneyInput` into `components/ui/money.tsx`,
the chart table into `components/ui/table.tsx`, `useSeesMoney` into `session.tsx` (it reads a role
and nothing else), and `ViewConfig` with `DEFAULT_VIEW` into `task-parts.tsx`, which both files
already imported `GroupBy` from.

What is left is the directory: 53 components in one folder is still 53 components in one folder.

> **Remaining.** Move `components/` into `modules/<name>/`, which makes the cross-capability imports
> that survive — `routes/projects.tsx` hosting the KPI and budget panels is the clearest — visible as
> imports rather than invisible as neighbours.

### 5. Nothing was code-split, so every workspace downloaded every feature — **fixed**

`npm run build` produced one **1 304 kB** chunk (385 kB gzipped) plus a lazily-loaded mermaid. Vite
warned about it. In that chunk, for a workspace with the optional features off, sat the budget
screens, the KPI screens, the register, the timesheet, the manual, and two locale catalogues nobody
had selected — roughly a sixth of the source tree, parsed and evaluated on a phone that would never
render a word of it. The switch already existed and `lib/nav.ts` already read it: a workspace without
budgets got no link to budgets and all of the code anyway.

| | Chunk | Gzipped |
|---|---:|---:|
| Before | 1 304 kB | 385 kB |
| After | **819 kB** | **253 kB** |
| | −37% | −34% |

Split out: `de` (138 kB) and `fr` (142 kB), `settings` (79), `budgets` (36), `infrastructure` (30),
`kpis` (27), `help` (13), `rates` (13), `timesheet` (1).

Three things this needed that "add `React.lazy`" does not say:

- **English stays static.** It is the fallback `translate` reaches for on a missing key *and* the
  catalogue the key type is derived from; neither survives being fetched. `main.tsx` awaits the
  detected locale before the first render, so a German reader gets German rather than a frame of
  English — the language equivalent of the theme flash the line above it prevents.
- **A capability's panels count as the capability.** `routes/projects.tsx` imported `ProjectKpis`
  and `MilestoneKpis` statically, which pulled all 1 676 lines of the KPI screen straight back into
  the first load and quietly cancelled the split. Both are fetched now, behind the switch at the
  call site rather than inside the component, because a check that runs after the import is too late
  to stop one. `ProjectBudget` was the same.
- **Splitting would have cost offline.** The service worker caches `/assets/` on first *request*, so
  a chunk nobody has opened is a chunk that is not on the device — and opening Settings on a train
  would have found nothing. The screens are warmed in `requestIdleCallback` after the app is up,
  narrowed by the same switches the navigation uses. Off the critical path, on the disk a second
  later. And because a chunk can still be missing — a deploy replaces the file whose fingerprinted
  name an open tab remembers — the route switch sits inside an error boundary that says so and
  offers a reload, rather than failing as a blank area and an uncaught rejection.

> **Remaining.** Chat, the board and the task sheet stay eager on purpose: a screen somebody reaches
> several times an hour must not spend a frame on a spinner to save bytes on a file they were always
> going to need. The next honest win there is not splitting but the mermaid and katex chunks, which
> are already lazy and are the largest things on disk.

### 6. The client store recomputes everything on every change

`lib/store.ts` keeps one global `version` counter. Any write to any entity bumps it, every
`useSyncExternalStore` listener fires, and all **241** `useQuery` / `useList` / `useRow` call sites
recompute. A chat message being typed in another channel invalidates the budget dashboard's
selectors.

This is fine at demo size and it is the right first version — the memo means each selector is cheap.
It is on this list because it is the one place where "everything is one module" is a *runtime*
property rather than a source-tree one, and because the fix is small.

> **Fix.** A version per entity table, and `useQuery(fn, deps, [entities])` subscribing only to what
> it reads. The registry already knows the entity names, so the per-table counters are one line.

### 7. Reads have no home, so the assistant and the screen can disagree

635 SQL statements across 46 server files; no query layer. The consequence is not duplication of
code, it is duplication of *definitions*: `mcp.ts`'s `deadlines_at_risk` calls work at risk if it is
due within 14 days, unstarted, blocked or unassigned; `web/lib/overview.ts` calls work `soon` if it
is due within 7 days and open. Both are defensible. Neither knows about the other. A person who asks
an assistant and then looks at the screen gets two different answers to what they think is one
question.

`routes/auth.ts` is the same problem in a different shape: 957 lines and 41 endpoints covering
sign-in, 2FA, sessions, the account, API tokens, workspaces, members, invites, unsubscribe links,
mail status, bounce handling, Telegram linking and push registration. Eight concerns, one file,
because there was no module for any of them to land in.

> **Fix.** Each capability owns a `queries.ts`: named, typed read functions, the only place its SQL
> lives, called by REST routes, MCP tools and reports alike. Where the definition must also hold on
> the client — "at risk", "overdue", "on track" — it goes in `shared` as a pure predicate over rows,
> and both sides call it. Then split `routes/auth.ts` along the modules its endpoints already belong
> to.

## The target: a kernel, capabilities and adapters

```
                         ┌──────────── adapters ────────────┐
                         │  mcp   rest   webhooks  calendar │
                         │  mail  push   telegram  share    │
                         │  s3    ai     oauth     transfer │
                         └───────────────┬──────────────────┘
                                         │  a protocol, a provider, a format
                         ┌───────────────▼──────────────────┐
                         │          capabilities            │
                         │  work  planning  pages  chat     │
                         │  time  budgets   kpis   infra    │
                         │  automation  ai-review  guide    │
                         └───────────────┬──────────────────┘
                                         │  entities, invariants, tools, queries, screens
                         ┌───────────────▼──────────────────┐
                         │             kernel               │
                         │  registry · write path · sync    │
                         │  identity · files · search       │
                         │  i18n · platform · design system │
                         └──────────────────────────────────┘
```

Three rules, and they are the whole architecture:

1. **Capabilities depend on the kernel, never on each other.** Where two genuinely need the same
   thing — a money input, a visibility hook, a table — that thing is kernel, not a shortcut between
   them. Finding 4 is what the rule is for.
2. **Adapters depend on capabilities, never the other way round.** An adapter is a translation of
   something the product already does into a protocol somebody outside speaks. If a capability needs
   an adapter, the capability is holding logic that belongs to it — `notifications` at 58 lines is
   that mistake seen from the other side.
3. **The kernel depends on nothing above it.** It is what remains when every capability is removed,
   and it must still start, sync, authenticate and serve an empty workspace.

What this buys, concretely: a capability can be added by adding a directory; switched off without
being loaded, on the server *and* in the browser; tested with the kernel and nothing else; and
removed by deleting a directory and one line of registration. None of those is true today for any of
the fifteen.

### Which ring a thing belongs in

The test is a question about failure, not about size. **If this were deleted, what breaks?**

- Everything, immediately, including an empty workspace → **kernel**.
- One area of the product; the rest keeps working → **capability**.
- One way of reaching the product; the product itself is unchanged → **adapter**.

`search` is kernel because the index is written in the same transaction as the row, so removing it
would change the write path. `trash` is a capability because tombstones would still exist, they would
just have no screen. `mcp` is an adapter because everything it does, a person can already do.

## The module contract

A capability is a directory on each side, and a manifest the kernel reads.

```
packages/server/src/modules/budgets/
  index.ts        the manifest below
  entities.ts     the registry entries this module contributes
  schema.sql      its tables, concatenated into the schema in dependency order
  invariants.ts   defaults, invariants and guards, registered per entity
  effects.ts      what happens after one of its rows changes
  visibility.ts   canSee* for its rows
  queries.ts      named reads — the only place its SQL lives
  tools.ts        its MCP tools
  routes.ts       endpoints the generic CRUD cannot express

packages/web/src/modules/budgets/
  index.ts        the manifest: destinations, lazy routes, settings panel
  routes.tsx      screens, loaded on demand
  components/     its own, not everyone's
```

```ts
export interface CapabilityModule {
  name: string;
  /** The workspace switch, if it has one. Absent means always on. */
  flag?: keyof WorkspaceFeatures;
  /** Registry entries. Merged into ENTITIES; the client derives its stores from the result. */
  entities: Record<string, EntityDef>;
  /** Write-path hooks, per entity. The dispatcher stays in the kernel. */
  defaults?: Partial<Record<EntityName, DefaultsHook>>;
  invariants?: Partial<Record<EntityName, InvariantHook>>;
  guards?: Partial<Record<EntityName, GuardHook>>;
  /** Reactions to a committed write. Called from the bus, not from writeEntity. */
  effects?: EffectHook[];
  /** "May this person see this row", for the rows this module owns. */
  visibility?: Partial<Record<EntityName, VisibilityRule>>;
  /** MCP tools. Omitted from the tool list when the flag is off. */
  tools?: ToolDef[];
  /** Named reads. The only place this module's SQL lives. */
  queries?: Record<string, QueryFn>;
}
```

Three things this deliberately does **not** do:

- **No dynamic loading, no plugin API, no third-party modules.** The manifests are imported
  statically by one registry file. This is a shape for the code in this repository, not an extension
  point for code outside it — a plugin API is a compatibility promise, and the project does not want
  one yet.
- **No new runtime dependency.** The registry is an array of objects and a `for` loop. That is the
  same trade `architecture.md` makes everywhere else, for the same reason.
- **No change to the sync protocol or the schema.** Every table keeps its name and every entity keeps
  its registry entry; what moves is which *file* the entry is written in. `schema.sql` is
  concatenated from the modules rather than replaced, so an existing database is untouched.

## Getting there

Ordered by ratio of value to risk. Each step ships on its own, keeps 1 303 tests green, and is
useful even if the next one never happens. Steps 1, 2, 3 and 5 are done; what is left starts at 4.

| # | Step | Touches | Risk | What it buys |
|---|---|---|---|---|
| 1 | ✅ Land `scripts/modules.mjs` and this document | new files | none | The map exists, is generated, and is checked in CI |
| 2 | ✅ Lazy-load capability routes and locale catalogues | `App.tsx`, `lib/i18n.ts`, `main.tsx`, `routes/projects.tsx` | low | First load 1 304 kB → 819 kB, gzipped 385 → 253; warmed in idle so offline is unaffected |
| 3 | ✅ Move the money widget, the chart table, `useSeesMoney` and `ViewConfig` down | 12 files | low | Both client knots gone |
| 4 | `repo.onWrite()`; `automation` registers at startup | 3 files | low | Kills the server knot with no change to transaction semantics |
| 5 | ✅ Move `storeFile` and `searchWorkspace` down out of `routes/` | 6 files | low | Zero layering exceptions — nothing left to cite as precedent |
| 6 | Split `lib/mcp.ts` into eleven `tools.ts` files | 1 file → 12 | medium | A capability's tools live with the capability; a switched-off feature ships no tools |
| 7 | Hook points in `writeEntity`; move the invariants out | `repo.ts` → 8 modules | medium | `repo.ts` becomes the ~400-line dispatcher it is described as |
| 8 | `queries.ts` per capability; the shared predicates for "at risk" | ~15 files | medium | One definition of a question, for the screen and the assistant |
| 9 | Per-entity store versions on the client | `lib/store.ts` | low | 241 selectors stop recomputing on every keystroke |
| 10 | Move `components/` and `routes/` into `modules/` on both sides | ~120 files | high | The directory listing finally matches the architecture |

Step 10 is last on purpose. It is the one that looks like the architecture and the one that delivers
the least: a rename of 120 files produces an enormous diff, invalidates every open branch, and
changes no behaviour. Doing it *after* steps 6–8 means the files being moved are already small and
already own their rules, and the move is mechanical. Doing it first would be a reorganisation
performed on the same tangle, which is how a codebase ends up with tidy directories and the same
2 370-line file.

### What this does not fix

Honest limits, so nothing here is oversold:

- **`repo.ts` will not get small.** After step 7 it is the merge, the transaction, the tombstones and
  the dispatcher. That is a few hundred lines that genuinely belong together, and no amount of
  modularity removes them.
- **The kernel stays a single node.** Modules do not change `nextSeq()` or the in-process bus, and
  step 4 deliberately does not either: inverting an import is not the same as making a call
  asynchronous, and only the second one buys a second replica. Every trade-off
  `architecture.md` accepts is still accepted.
- **`i18n` stays the largest kernel module.** 7 532 lines is three catalogues of 2 249 keys. Step 2
  stops shipping the two nobody asked for; it does not make the catalogues smaller, and it should
  not — the compile error on a missing key is worth more than the file size.
- **Modules are not a permission boundary.** A capability is a unit of code, not of trust. Who may
  see what is still `canSeeProject` and the workspace check in front of it, exactly as
  `architecture.md` describes, and moving visibility rules into modules must not make that check
  optional.

## The rules, and who enforces them

`scripts/modules.mjs` runs in CI. It regenerates the tables above and fails if they have drifted,
and it checks four rules. Each rule has an escape hatch that must be *named*, never counted — a
threshold is a budget somebody will spend, and a named exception has to be deleted by the person who
fixes it.

1. **Every source file belongs to exactly one module.** A file nothing claims fails the build. This
   is the load-bearing rule: it forces the question "which capability is this?" while somebody still
   knows the answer.
2. **Packages point one way.** `shared` imports neither of the others, `web` never imports `server`,
   `server` never imports `web`, and `@kolibri/shared` is the one bare specifier that may cross.
3. **Layers point one way.** Inside the server, `lib/` is below `routes/`. **No exceptions** —
   `KNOWN_LAYERING` is empty, so there is no grandfathering left and the next import from `lib/` into
   `routes/` fails the build with nothing to point at as precedent.
4. **No import knots.** Reported as the whole set of files that can reach each other rather than as
   one lap around it, so the list does not reshuffle when an unrelated file is renamed. **One left**,
   named in `KNOWN_KNOTS`: the write path and the rules engine, which step 4 unpicks.

```bash
npm run check:modules      # the four rules and the tables; exit 1 on a violation
npm run modules            # the inventory on the terminal
npm run modules -- --fix   # rewrite the tables above
```

The rules the script cannot check are the two in [The target](#the-target-a-kernel-capabilities-and-adapters)
that are about direction rather than shape — a capability importing another capability, an adapter
being imported by one. Both become checkable once step 10 puts the modules in directories, and the
script has a place to grow into. Until then they are review questions, and this file is what to
review against.
