# Languages

Kolibri ships in **English**, **German** and **French**. All three are catalogue
files — English is not special-cased anywhere in the code, it is simply the
catalogue every other locale is typed against.

Pick a language under **Settings → Profile → Sprache/Language/Langue**, or on the
login screen before you have an account.

> **French is machine-written and has not been read back by a native speaker.**
> The app says so under the picker, in the language you have just chosen, rather
> than letting somebody find out from an odd sentence three screens later. It is
> shipped anyway, on the reasoning that an unchecked catalogue is worse than a
> good one and better than none — as long as nobody is misled about which they
> have. Corrections are the cheapest contribution this project accepts: one
> file, no build step, and the types refuse a missing key. If a sentence reads
> like it was written by a machine, it was; send the fix.

## How a language is chosen

In order, first match wins:

1. **The choice on this device** — `localStorage['kolibri.locale']`, set by the
   picker. It outranks everything, so a shared laptop can stay in one language
   while the account is in another.
2. **The account** — `users.locale`, set by the same picker and synced. A device
   that has never been told otherwise adopts it on sign-in, so a new phone comes
   up in the right language without being configured.
3. **The browser** — the first entry in `navigator.languages` Kolibri has a
   catalogue for.
4. **English.**

The server has the same question to answer for text it writes on its own —
notification titles and emails — and answers it differently, because there is no
browser in the room:

1. `users.locale` for the recipient,
2. `KOLIBRI_DEFAULT_LOCALE` (default `en`).

Notification titles are rendered **per recipient, at the moment they are
created**: a row belongs to exactly one person, so it is stored in that person's
language and never needs translating again. Ada writing a comment in an English
interface produces a German notification for Lin, and vice versa. Emails are
rendered the same way, at send time.

The one exception is an invitation, where the recipient has no account yet: it
goes out in the *inviter's* language, which is the best guess available.

## What is not translated

- **Your content.** Project names, task titles and page bodies are data, not
  interface. The one exception is the *first* set of workflow states and labels
  a new project is given: those are written in the creator's language, because
  a fresh project should not open in a language the team does not use. They are
  ordinary editable rows from that moment on — rename them to whatever your
  team says out loud.
- **API error messages.** They are read by developers, logs and clients, not by
  the interface, so they stay English and stable.
- **Dates and numbers** are not translated but *formatted*: `Intl.DateTimeFormat`,
  `Intl.RelativeTimeFormat` and `Intl.PluralRules` all follow the active locale.

## Right-to-left

`LOCALE_DIR` in `lib/i18n.tsx` maps each locale to `ltr` or `rtl`, and the
provider puts it on `<html dir>`. The stylesheet uses logical properties
throughout (`padding-inline-start`, `inset-inline-end`, `border-inline-start`),
so a mirrored layout needs no CSS of its own, and icons that mean *forwards*
rather than naming a thing are flipped by `[dir='rtl'] .icon-dir`.

Both shipped locales are left-to-right, so this has only been verified by
forcing `dir="rtl"` in a browser and checking that nothing scrolls sideways or
falls out of frame. Nobody has seen it with real right-to-left text.

## Adding a language

Four steps, and the build stops you if you miss one.

1. Copy `packages/web/src/kernel/i18n/locales/en.ts` to `packages/web/src/locales/xx.ts`,
   change the export to `export const xx: Catalogue = { … }` and translate the
   values. `Catalogue` is derived from the English file, so a missing or
   misspelled key is a **compile error**, not a `[missing]` at runtime.
2. Register it in `packages/web/src/kernel/i18n/i18n.tsx`:

   ```ts
   import { xx } from '../locales/xx';
   export const LOCALES = { en, de, fr, xx } as const;
   export const LOCALE_NAMES: Record<Locale, string> = { en: 'English', de: 'Deutsch', fr: 'Français', xx: '…' };
   // Until a speaker of it has read the catalogue back:
   export const UNREVIEWED: Partial<Record<Locale, boolean>> = { fr: true, xx: true };
   ```

   The picker, `detectLocale()` and the server's validation all read from
   `LOCALES` — there is no second list to update.
3. Add the same locale to `packages/server/src/kernel/i18n/i18n.ts` for notification
   titles, emails, and the workflow a new project is seeded with. It is a much
   smaller catalogue (about 35 strings) and deliberately separate: those strings
   have no counterpart in the UI, and sharing one would mean the server
   importing a React module. Add a `LOCALE_DIR` entry too if it is
   right-to-left.
4. Run `npm test`. `packages/server/test/i18n.test.ts` finds every file in
   `locales/` on its own — there is no list of languages to update in the tests —
   and checks that the catalogues have the same keys in both directions, that no
   `{placeholder}` was lost in translation, that `_one`/`_other` plural pairs are
   complete, that every key the interface uses exists, and that no user-visible
   string is hard-coded in a component.

### More plural forms than two

`_one` and `_other` are what English, German and French need. A language with
more — Polish has `one`, `few`, `many`, `other`; Russian and Arabic have their
own sets — needs no code: the translator asks `Intl.PluralRules` for the
category and looks up `key_<category>`, falling back to `key_other` when a form
is missing. Write as many as the language has:

```ts
'task.count_one': '{count} zadanie',
'task.count_few': '{count} zadania',
'task.count_many': '{count} zadań',
'task.count_other': '{count} zadania',
```

This used to be a claim rather than a fact. It is now driven through Polish's
four categories in `i18n.test.ts`, against the same two lines the interface
runs.

Optionally run the browser walkthrough in the new language:

```bash
KOLIBRI_LOCALE=xx node scripts/smoke.mjs   # screenshots land in /tmp/shots-xx
```

It needs the seven labels it clicks on added to the table at the top of that
file. A missing translation then shows up as a selector that no longer matches,
which is a more useful failure than a screenshot nobody looks at.

## Writing catalogue entries

- Keys are `area.thing`: `task.addSubtask`, `project.deleteConfirm`. The area
  matches roughly one screen, so a translator can work through a file in the
  order a user meets the strings. The largest area is `guide.*` — the manual
  built into the app, including every sentence narrating an animation, so a new
  locale gets an explained product rather than a translated menu bar.
- Interpolation is `{name}`: `'page.updated': 'Updated {time}'`. An unknown
  placeholder is left as written rather than replaced with `undefined`.
- Plurals are `key_one` / `key_other`, selected through `Intl.PluralRules` when
  a `count` variable is passed. Call them by the base key:

  ```ts
  t('task.labelCount', { count: 3 })   // "3 labels" / "3 Labels"
  ```

  Languages with more forms (`_few`, `_many`, `_zero`) work the same way; add the
  forms that language needs and `_other` catches the rest.
- Do not concatenate. `t('project.doneCount', { done, total })` is one string a
  translator can reorder; `{done}/{total} + ' done'` is not.
- Values that are *chosen* rather than written — a priority, a workflow group, a
  role — get their key built by a helper in `lib/i18n.tsx` (`priorityKey`,
  `groupKey`, `relationKey`, `roleKey`), so the cast lives in one place instead
  of at every call site.

## Environment

| Variable | Default | Meaning |
|---|---|---|
| `KOLIBRI_DEFAULT_LOCALE` | `en` | Language for notifications and emails sent to someone who has not picked one. A region suffix is ignored (`de-AT` → `de`). |
